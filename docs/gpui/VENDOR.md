# Glint's changes to the vendored GPUI

*`vendor/` holds gpui-pre 0.3.12, gpui-pre-windows 0.3.12, gpui-base 0.9.1 and gpui-component 0.9.1 (the last two from gpui-kit 0.9.1), patched for Glint and used through the workspace's `[patch.crates-io]`. Updating GPUI means carrying these changes forward, so every change is listed here with why.*

| Where | Change | Why |
| :--- | :--- | :--- |
| gpui-pre, gpui-pre-windows, gpui-base | The right-to-left fix: [rtl-fix.patch](rtl-fix.patch) (DirectWrite glyph placement and bidi levels, visual-order runs, cluster-based caret and hit testing, `x_ranges_for_index_range`, per-stretch selection in Input) | Arabic text laid out and edited correctly (migration plan, appendix) |
| gpui-pre `resources/windows/gpui.manifest.xml` | Glint's application manifest: GPUI's own (asInvoker, Windows 10/11, PerMonitorV2, SegmentHeap, Common Controls 6) plus `longPathAware` | gpui-pre-platform always turns on gpui-pre's `windows-manifest` feature, which links this manifest into every GPUI binary; a second manifest in Glint.exe fails the link (CVT1100). Test binaries get the same manifest as the app. Glint.exe's own resources carry the icon and version info only |
| gpui-pre-windows `window.rs`, `set_window_placement` | Skips the placement asked for at open when the window is already visible | Glint opens its main window hidden, puts it in its saved place and shows it itself (no flash in the wrong place). Without this, the first `activate_window()` (gpui-component's notifications call it) would move the window back to the open-time bounds |
| gpui-pre-windows `window.rs`, `WindowsWindow::new` | A window opened with `show: false` gets its requested placement at once (hidden) | Glint shows its hidden windows with ShowWindow (posted, outside GPUI's callbacks); without this a hidden window kept CreateWindowEx's default size (Quick Search came up 1920 x 1010) |
| gpui-pre `window.rs`, `Window::dispatch_event` | A file drag from another app (`FileDropEvent::Entered`, `Pending`, `Submit`) sets the input modality to mouse | The events are turned into mouse moves and a mouse up, but the modality was set from the original event, so after any key press it stayed keyboard, hover (which every drop listener checks) stayed off, and a drop from File Explorer reached no view until the mouse had moved over the window |
| gpui-pre `text_system/line_layout.rs` (`layout_wrapped_line`, `WrappedLineLayout`) and `text_system/line.rs` (`paint_line`, `paint_line_background`) | Right-to-left paragraphs wrap in reading order: breaks come from the text's break opportunities at grapheme and cluster boundaries (widths from the single-line shaping's advances keyed by logical index), each row is laid out as a line of its own and the rows' glyphs are concatenated, row k starting at its own x, so the boundary-based painting works unchanged. A paragraph whose first strong letter is right-to-left sets each row in an RLE..PDF embedding (the platform has no paragraph direction), whose runs arrive in reading order and are sorted left to right; a row's trailing spaces hang (glyphs kept, zero width, at the row's end). `index_for_position`, `closest_index_for_position` and `position_for_index` work per row once the layout has right-to-left glyphs (x from the row's left edge). Painting finds a glyph's decoration run by text index (`DecorationCursor`), because right-to-left glyphs come in screen order. Layouts with no right-to-left text take the old path unchanged | A wrapped Arabic paragraph (Word preview, Markdown, mail, books) broke inside words and its second row ran past the start edge: the whole paragraph was shaped as one visual-order line and wrapped as if x grew with the text index |
| gpui-base `text/node.rs` (`NodeContext::base_rtl`, `Paragraph::render_aligned`, `BlockNode::first_strong_rtl`, `render_list_item_row`, `render_list_item`, `render_block`: blockquote and code block, table cells), `text/state.rs` (`TextViewState::render` sets `base_rtl`), `text/utils.rs` (`first_strong_rtl`, `has_rtl_text`), `text/inline_flow.rs` (`prepaint`) | Markdown blocks take their own direction (HTML's `dir="auto"`). The window's direction is read once per frame from the alignment the view inherits (left: left to right, right: right to left, centered: nothing changes). A paragraph, heading or table cell whose first strong letter reads the other way is set in a full-width box aligned to its own start edge (text that is not in a right-to-left script gets its box moved to the end instead, since it is only as wide as its longest row); in a right-to-left window every paragraph is aligned explicitly. A list item that reads right to left puts its marker (and the task checkbox) on the right, with its continuation and nested lists indented from the right; a blockquote that does has its bar and padding on the right. Code blocks stay left to right. An inline flow (a paragraph with code spans, math or pictures in it) that starts at the right is mirrored in its own width, line by line, so its fragments read from the right. English text in an English window takes the old path unchanged | An Arabic paragraph in the Markdown preview of an English window wrapped correctly but hugged the left edge, its short last row at the left; in an Arabic window an English one was drawn at the right. List markers and quote bars were always on the left |
| gpui-pre `wheel_glide.rs` (new; `wheel_notch_glides` and `wheel_glide_advance` are public), `elements/div.rs` (`paint_scroll_listener`), `elements/list.rs` (the scroll listener, `ListState::glide_key` and `glide_step`); gpui-base `input/base/state.rs` (`on_scroll_wheel`, `wheel_glide`, `wheel_glide_step`, two fields) | A notch of a mouse wheel glides: whole-line scrolls (`ScrollDelta::Lines` of a line or more) move a target, and the offset closes in on it over the next frames (an exponential ease with a 50 ms time constant, steps on whole device pixels, the first step taken in the event itself). A notch the other way drops what was left; anything else that moves the offset (clamping at an end, the scroll bar, a jump to an item) ends the glide. Fine-grained deltas (a precision touchpad) are applied as they come, and so is everything under `App::reduce_motion`. A wheel's line is a third of 100 px at the usual text size (a notch of three lines moves 100 px, as in a browser; GPUI's own measure, the window's text line, gave 62 px), following the rem size. The kit's text editor scrolls itself (its own offset and bounds, three of its own lines a notch), so it runs the same steps through the two public functions | Applied at once, a notch jumped the list 60 px in one frame: measured in the release build, a file list scrolled with the wheel drew one frame per notch, about ten a second. This is what made scrolling feel worse than in the web app, which smoothed the wheel as browsers do |
| gpui-pre `elements/div.rs` (`set_hover_fade`, `HoverFade`, `refine_by`, `mix_colors`, `compute_style_internal`, two fields of `InteractiveElementState`) | Hover styles can fade: with `set_hover_fade(Some((in, out)))`, the `.hover(..)` and `.group_hover(..)` styles of elements that have an id blend their background, border and text colors and their opacity in over `in` and out over `out` (eased, reversible mid-way, alpha-weighted so nothing passes through gray); the rest of the hover style still switches at once. Only the paint phase fades (it is the one that knows what the pointer is over); layout and prepaint see what they saw before. Off by default, for elements without an id, and under `App::reduce_motion`. Glint turns it on in `theme::motion::init` (70 ms in, 160 ms out) | Every button, row, tab and menu item switched its hover fill in a single frame. One switch in the engine gives the whole app, the kit's controls included, the short fade Windows 11's own controls have, instead of a transition written into every view |
| gpui-pre `window.rs` (`frame_log_enabled`, `frame_log_at`, `frame_log_line`, and marks in the frame callback, `draw_roots` and the input callback) | With `GLINT_FRAME_LOG` set in the environment, every drawn frame prints `frame at=… draw=… layout=… prepaint=… paint=… a11y=… present=…` (milliseconds) to stderr, and every input `input kind=… at=… ms=…` (`at` on the frames' clock, so the wait from a press to its frame can be read off the log). One atomic load per frame when it is not set | Measuring how the interface feels, in the real app, without GPUI's `profiler` feature (which needs another crate). The numbers behind the two rows above came from it |
| gpui-pre-windows `platform.rs` (`pending_devices`, `WindowsPlatform::new`, `attach_gpu`) | The DirectX devices are made on a thread of their own, started as the first thing the platform does; `attach_gpu` (run by `Platform::run` before the application's code) takes them from it, and makes them itself if that thread failed or on a later attach | Making the devices loads the display driver: 155 to 175 ms on this PC, the longest single step of a start, and the main thread waited for it after it had made everything else. Now the text system, the platform's window and the rest are made meanwhile: the wait at `run` fell from 175 ms to 85 ms. Measured with `GLINT_BENCH_START` (the marks in `glint_core::startup`) |
| gpui-pre-windows `window.rs` (`WindowsWindow::frame_waker`; `last_draw`, `last_draw_early`, `early_frame_asked`, `frame_is_early`, `early_frames` and `in_frame` in the window's state, kept in `draw`), `events.rs` (`draw_window` says whether the frame it handles is the early one, and that a frame is being handled), `vsync.rs` (`refresh_interval`) | A window draws as soon as it has something to draw instead of at the display's next tick, through GPUI's `frame_waker` hook (unused on Windows until now), which marks the window as needing paint: when it has drawn nothing for a whole refresh (it was at rest), and once more if it changes again before the tick has drawn anything (a press is usually answered twice within a few milliseconds: by the control that took it, then by the folder or the results it asked for). Nothing is asked for from inside a frame (an animation asking for its next one), while an early frame is still to be handled, or once the tick has drawn. So frames that flow are drawn once a refresh as before, with at most two early ones where they start. `GLINT_EARLY_FRAMES=0` turns it off | Frames were only ever drawn on the display's tick (the vsync thread invalidates every window then), so a press on a resting window waited for the next tick, and what it drew reached the screen a refresh later than it could have. Measured with the frame log at 144 Hz (`GLINT_EARLY_FRAMES=0` against the default, the same build): the frame for a key press began 3.1 ms after the key (median) and now begins 1.5 ms after it, which is the handling of the key itself; it was presented 9.7 ms after the key and is presented 8.2 ms after (5 ms with the rest of that wave's work). At 60 Hz the wait it removes is 8 ms on average and up to 17 |
| gpui-component (vendored unchanged from crates.io, then:) `dialog/entrance.rs` | `DialogEntrance::FadeSlide` is the default (it was `SlideDown`) | The legacy entrance slid every dialog down from the top of the window over a quarter of a second. The new default is in place from its first frame and settles a few pixels within the theme's normal duration (170 ms in Glint) |
| gpui-component `notification.rs` | A notice arrives in 220 ms from 20 px away on `cubic-bezier(0.16, 1, 0.3, 1)` and leaves in 140 ms (it was 400 ms from 96 px away on CSS's `ease`, and 200 ms out) | Notices follow most things Glint does (a copy, a move, a rename undone); a slide long enough to watch made each of them feel slow |
| gpui-component `popover.rs` | `DROPDOWN_ENTER_DURATION` is 120 ms (it was 150) | Menus and drop-downs are opened constantly; they are there by the time the eye is |
| gpui-base `input/base/state.rs` (`InputState::reveal_line`) | Shows a (0-based) line and selects it without taking the keyboard: the cursor moves to the line's start (which scrolls it into view) and the selection runs to its end. `set_cursor_position` does the first half but focuses the editor | A line a search found inside a file, pressed in the list, is shown in the file's preview while the keyboard stays in the list |
| gpui-component `Cargo.toml` (`resvg`) | resvg 0.46.0 (it was 0.45.1) | gpui-pre already uses 0.46.0: one copy of resvg, usvg, tiny-skia and the crates under them instead of two. The native menu's icon drawing (`native_menu/windows.rs`) needed no change |
| gpui-base and gpui-component `Cargo.toml` (`windows`), gpui-base `reduce_motion.rs`, gpui-component `native_menu/windows.rs` | windows 0.62 (it was 0.58), as in the rest of the build: `BOOL` comes from `windows::core`, `LoadLibraryExW`, `GlobalFree` and `CreateDIBSection` take `None` for their optional handles, `CreateStreamOnHGlobal` takes `true`. gpui-component's `speech` feature (off in Glint) was not updated | One copy of the windows crates: windows, windows-core and their macro crates 0.58 were compiled for these two alone |
| gpui-pre and gpui-pre-windows `Cargo.toml` (`image`) | `image` without its `dds`, `exr`, `ff`, `hdr`, `qoi` and `tga` codecs | GPUI draws the formats `ImageFormat` names (PNG, JPEG, WebP, GIF, BMP, TIFF, ICO, PNM) and SVG, and Glint hands it nothing else (`preview/picture.rs` sniffs first; design files' pictures are PNG). Only a Markdown picture in one of those six formats no longer shows |
| gpui-pre, gpui-base, gpui-component, gpui-pre-windows (the crates' own files) | Their examples (gpui-pre's 56 files, 5 MB), tests, benches and Cargo.lock files are gone, with the `[[example]]`, `[[test]]` and `[[bench]]` entries that named them | Glint builds none of them (path dependencies build their libraries alone), and gpui-component's tests read files the crate never shipped |
